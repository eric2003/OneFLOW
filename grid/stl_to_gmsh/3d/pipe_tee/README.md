# Pipe Tee Mesh Benchmark

This benchmark separates geometry shape from geometry provenance. A Case must declare
all four catalog fields:

- `benchmark_family`: `pipe_tee`
- `geometry_variant`: `square_duct` or `circular_duct`
- `geometry_source`: `occ_native`, `occ_to_stl`, or `manual_stl`
- `volume_mesh_method`: `automatic_tetrahedra`

## Geometry-source routes

| Source | Geometry variant currently registered | Construction and meshing path |
| --- | --- | --- |
| `occ_native` | Circular duct | Build the connected three-port fluid volume with Gmsh OpenCASCADE Boolean operations and mesh that OCC volume directly. No STL re-import is used for volume meshing. |
| `occ_to_stl` | Circular duct | Build the same circular-duct geometry with OCC, export its boundary to STL, then re-import that STL and generate the tetrahedral volume mesh through the generic STL mesher. |
| `manual_stl` | Square duct | Use a deterministic, hand-authored low-facet square-duct STL surface, then run the generic STL-to-tetrahedra path. The current reference asset is generated by an explicit facet script; it is not an OCC export. |

The existing Mesh Projects page also supports importing an externally supplied STL.
That user-selected import is kept distinct from the checked-in hand-faceted square
reference Case; it should not be mislabeled as an OCC-generated STL.

## Comparison contract

The square and circular variants share the same abstract three-port internal-flow
contract: a connected fluid volume, two ends of the straight main duct, one
perpendicular branch, and a wall boundary. They are geometrically different
cross-sections, not identical surface meshes.

The operating modes are:

- `main_inlets`: both main-duct ends are inlets; the branch is the outlet.
- `branch_inlet`: the branch is the inlet; both main-duct ends are outlets.
- `benchmark`: retain the original OECD/NEA-Vattenfall inlet/outlet assignment
  where that geometry supports it.

For OCC and STL routes, preserve the three port identities in geometry manifests
and validation evidence even when the Gmsh Physical Groups are aggregated as
`inflow` and `outflow`.

## Validation workspace

Mesh-to-CFD output is placed outside the source tree under
`%USERPROFILE%/.oneflow/mesh-validation/pipe_tee/` and is partitioned by:

`geometry_variant / geometry_source / volume_mesh_method / case_id / operating_mode`.

This avoids using a descriptive source directory as a destructive runtime workspace.
Each Case owns a separate leaf directory. The validation report records all four
geometry identity fields, the operating mode, mesh evidence, conversion evidence,
OneFLOW ingestion, and the bounded CFD smoke-test result.

The CFD smoke test is an execution check only. Mesh-quality acceptance thresholds
and physical CFD accuracy remain separate, explicitly unclaimed checks.
