# OneFLOW Workbench 架构备忘录

## 1. 产品定位

OneFLOW Workbench 是面向 OneFLOW 的工程工作台，而不只是启动几个算例的 GUI。它应与求解器和网格基础设施相辅相成、共同演进，逐步覆盖工程管理、工作流编排、运行追踪、网格校验、结果分析、流场可视化、数据对比、报告生成，以及受控的开发诊断辅助。

本备忘录记录长期设计意图。它指导实现，但不是不可修改的教条；架构应根据真实使用场景、测试和维护成本持续修订。

## 2. 核心概念

- **Project / 工程**：组织输入、配置、网格、求解结果和工程元数据的边界。
- **Workspace / 工作区**：承载可写运行副本、日志、缓存和生成物的位置。不得默认覆盖受版本控制的输入。
- **Case / 算例**：可独立选择和运行的已有工程目录及其配置；算例库用于发现和描述算例，不决定每次运行的执行位置。
- **Run mode / 运行模式**：单算例运行、多算例运行或依赖工作流，分别表达单个对象、无显式依赖的有序集合、以及存在输入输出依赖的任务图。
- **Workspace / 运行空间**：承载可写运行副本、日志、缓存和生成物的位置。单算例运行应明确选择在源算例目录执行、复制到 OneFLOW 默认运行空间，或复制到用户指定的运行目录。
- **Workflow / 工作流定义**：可命名、编辑、保存、复制和删除的执行计划；多算例工作流只表示无显式依赖的有序执行，依赖工作流则明确声明输入、输出与任务依赖。
- **WorkflowRun / 工作流运行记录**：某次工作流执行的不可混淆记录，包括时间、可执行文件、状态、日志引用、步骤结果和产物。
- **Artifact / 产物**：网格摘要、网格文件、流场、对比结果、日志、报告等可引用文件。
- **Diagnostic / 诊断**：带来源、位置、严重程度和建议的工程或编译问题。
- **Comparison / 对比**：对齐不同运行、数据集或基准结果的可复现比较任务。

工作流定义和运行记录必须分离。删除工作流定义不得隐式删除历史记录、源输入或运行产物。运行记录应尽可能保留当时使用的可执行文件路径、参数、输入快照引用和 OneFLOW 版本信息，以支持追溯。

## 3. 架构边界

1. **Domain / Models**：表达工程、工作流、运行、步骤、产物和诊断等概念，不依赖 Qt。
2. **Repositories**：负责版本化数据格式、持久化、加载和校验；定义数据与运行历史应分开存储。
3. **Execution Services**：构造参数列表、准备工作区、启动进程、采集日志、处理取消和记录结果。不得通过 shell 字符串拼接命令。
4. **Validation and Analysis Services**：独立执行工程校验、网格拓扑/几何检查、求解结果分析和数据对比。
5. **Presentation**：Qt 界面负责展示、编辑和用户交互，不应把持久化规则、进程控制和科学计算逻辑堆进窗口类。
6. **Adapters**：文件格式、可视化后端、报告格式和 OneFLOW 现有接口通过适配器接入，避免核心模型绑定单一 GUI 或文件格式。

尽量让核心服务可以在没有 Qt 的环境下进行单元测试。不要为了抽象而抽象：优先采用清晰的数据模型和小型服务，只有在真实需求出现时再引入扩展点。

## 4. 工作流语义

界面启动时先显示活动选择页，而不是默认进入 Case Workbench。用户应先选择运行已有算例、运行多个独立算例、运行依赖工作流，或进入测试、运行历史和网格布局工具。

运行入口应明确区分以下三种语义：

- **单算例运行（Single Case Run）**：选择一个算例，并选择源目录、默认运行空间或指定运行目录。
- **多算例运行（Multi-Case Run）**：运行多个没有显式依赖关系的算例；执行顺序可以由用户指定。
- **依赖工作流（Dependency Workflow）**：通过声明的产物和依赖边安排执行；前置任务失败或产物缺失时，不应继续执行依赖它的任务。

工作流应支持有序步骤，并明确区分不同执行语义。例如：

- 单个算例的隔离运行；
- 一次 OneFLOW 进程接收多个有序目录参数；
- 工程或输入校验；
- 构建和测试；
- 网格摘要与拓扑/几何检查；
- 流场分析、数据对比和报告生成。

这些语义不能被含糊的“运行多个算例”选项混为一谈。每个步骤应有明确的输入、输出、状态和失败语义。失败后的行为（停止、继续或清理）应由工作流策略决定并记录。

工作流定义采用带版本号的 JSON 格式。加载时验证版本和必需字段；未知版本应明确报错，不得静默误读。用户可通过文件配置和 GUI 编辑同一模型，避免出现两套互不兼容的状态。

## 5. 历史、复现和删除规则

- 每次执行都创建独立运行 ID 和运行记录。
- 运行历史按时间可查，并可按工作流筛选。
- 定义的删除与历史的保留相互独立。
- 运行目录和输入副本应可追溯，避免覆盖源算例。
- 状态、返回码、日志引用、步骤结果和产物引用应作为数据保存，而不只显示在瞬时 UI 控件中。
- 清理运行产物应是明确、可审计的独立操作，而不是删除定义的副作用。

## 6. 编译诊断和自动修改

Workbench 可以逐步获得编译诊断和辅助修复能力，但必须采用可审查流程：

1. 收集编译器输出和结构化诊断；
2. 定位相关源文件、构建目标和依赖关系；
3. 给出原因解释和候选补丁；
4. 展示差异并由用户批准；
5. 在隔离工作区应用修改；
6. 重新构建并运行相关测试；
7. 记录补丁、验证结果和失败原因。

不能把每个编译错误都假定为缺少 include。问题也可能来自目标依赖、包含目录、宏定义、平台差异或错误的模块边界。不得在未展示差异、未获批准时直接修改用户源文件。

## 7. Python 与 C++/Qt 的协同

允许 Python 和 C++/Qt 共同演进，但应由职责而不是语言偏好决定边界：

- Python 适合早期工作流存储、编排、测试、诊断处理和报告生成；
- Qt 负责桌面交互；C++ 组件适合确有必要的高性能可视化、原生集成和复杂交互；
- 两侧共享稳定、可版本化的数据契约，不维护两套相互竞争的工程状态；
- 不因“最终可能使用 C++”而阻止当前有测试覆盖的 Python 服务演进，也不把所有逻辑永久塞进 Python。

## 8. 渐进路线

1. 建立版本化工作流定义、独立运行历史和不依赖 Qt 的存储/执行服务。
2. 提供活动选择页，并实现单算例运行位置选择、多算例无依赖运行和依赖图运行，明确记录不同语义。
3. 接入工程校验、网格摘要、拓扑与几何验证、构建和测试。
4. 增加流场查看、结果数据对比、基准分析和报告生成。
5. 引入结构化编译诊断、用户批准的补丁和自动验证。
6. 根据性能和交互需求评估 C++/Qt 组件，而不是预先重写整个应用。

每一阶段都应有独立服务测试和清晰的用户可见结果。不要一次性重写整个界面，也不要把所有功能堆到主窗口中。

## 9. 当前落地原则

首个实现切片应建立工作流定义与运行历史的独立持久化，并测试创建、加载、更新、删除、版本校验和历史保留。随后再把现有目录运行方式纳入工作流模型。设计文档中的未来能力不是声称已经实现的功能；实现状态必须由代码和测试证明。
